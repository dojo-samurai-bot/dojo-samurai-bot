# Манифест синхронизации «Мой мир» / «Наш мир» v2

## Цель

Обеспечить уверенную офлайн-работу и безопасную синхронизацию минимум между 5 устройствами одновременно, с запасом до 20 зарегистрированных и 10 активных устройств.

## Неприкосновенные принципы

1. Каждое устройство всегда работает из локальной базы.
2. Любое пользовательское изменение сначала атомарно сохраняется локально.
3. Потеря интернета не блокирует создание, редактирование, выполнение и отмену записей.
4. Сервер никогда не заменяет всю базу версией одного устройства.
5. Синхронизация передаёт уникальные операции, а не полные снимки базы.
6. Повторная доставка одной операции безопасна и не создаёт дублей.
7. Критичные конфликты не разрешаются молча.
8. Удаление выполняется логически через tombstone и корзину.
9. История изменений и финансовых операций не стирается.
10. Google Таблица является сменным серверным хранилищем, а не частью интерфейса приложения.

## Идентификаторы

Каждое устройство получает постоянный `deviceId`.

Каждая сущность получает постоянный UUID:

- `guestId`
- `bookingId`
- `taskId`
- `purchaseId`
- `transactionId`

Каждое изменение получает уникальный `operationId`.

ID создаются локально и не требуют интернета.

## Локальная транзакция

Каждая команда пользователя выполняется одной транзакцией:

1. обновить локальную сущность;
2. добавить операцию в `outbox`;
3. обновить интерфейс.

Если приложение аварийно закрыто, операция остаётся в очереди.

## Формат операции

```json
{
  "operationId": "uuid",
  "deviceId": "uuid",
  "entityType": "guest",
  "entityId": "uuid",
  "action": "patch",
  "changes": { "phone": "+79991234567" },
  "baseVersion": 7,
  "clientCreatedAt": "2026-08-02T05:00:00.000Z",
  "schemaVersion": 2
}
```

## Серверный журнал

Сервер:

1. принимает операции пачками;
2. дедуплицирует по `operationId`;
3. обрабатывает пачки последовательно под блокировкой;
4. присваивает каждой принятой операции монотонный `serverSequence`;
5. возвращает подтверждение для каждой операции;
6. отдаёт устройству изменения после его `lastServerSequence`.

## Слияние

- Изменения разных полей одной сущности объединяются.
- Некритичные одновременные изменения одного поля применяются по серверному порядку с сохранением истории.
- Комментарии и заметки предпочтительно добавляются как отдельные события, а не перезаписываются.
- Критичные поля создают явный конфликт при несовпадении `baseVersion`.

Критичные данные:

- даты брони;
- стоимость, скидка, предоплата, остаток и депозит;
- статус оплаты;
- финансовые операции;
- удаление и восстановление брони.

## Финансы

Финансы хранятся как неизменяемый журнал событий. Исправление выполняется новой корректирующей операцией, а не переписыванием старой суммы.

## Удаление

Удалённая сущность получает:

```json
{
  "deleted": true,
  "deletedAt": "ISO-8601",
  "deletedByDevice": "uuid"
}
```

Tombstone хранится на сервере минимум 90 дней. Старое офлайн-устройство не может вернуть удалённую запись.

## Цикл синхронизации

Синхронизация запускается:

- через 2–5 секунд после локального изменения;
- при появлении сети;
- при открытии и возврате приложения на экран;
- каждые 1–2 минуты, пока приложение активно;
- вручную по кнопке.

Фоновый таймер Android не является единственным механизмом.

## Надёжность

Обязательны:

- повторная отправка с увеличивающейся задержкой;
- ограниченные пачки;
- отдельные статусы `pending`, `sending`, `acked`, `failed`, `conflict`;
- сохранение подтверждения только после ответа сервера;
- контроль схемы и версии данных;
- журнал ошибок и диагностика;
- ежедневный серверный снимок;
- ручной экспорт и восстановление;
- проверка целостности локальной базы.

## Пользовательские статусы

Приложение показывает:

- `Синхронизировано`;
- `Офлайн · N изменений ожидают отправки`;
- `Ошибка синхронизации · данные сохранены локально`;
- `Есть конфликты · требуется проверка`.

## Запрещённая логика

Нельзя:

- считать базу одного телефона единственно правильной;
- загружать весь локальный JSON и заменять им сервер;
- определять запись по номеру строки, имени или позиции в массиве;
- удалять данные физически при первой команде;
- повторно применять уже принятую операцию;
- молча перезаписывать критичное поле при конфликте.

## Целевая схема

```text
Локальная IndexedDB каждого устройства
        ↓
Надёжный outbox уникальных операций
        ↓
Серверный API с дедупликацией и последовательной обработкой
        ↓
Общий журнал serverSequence
        ↓
Получение и применение только недостающих операций
```

Этот документ является обязательным архитектурным контрактом для всех последующих изменений синхронизации.
